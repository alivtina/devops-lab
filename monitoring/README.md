# Kubernetes Monitoring with Prometheus

This lab demonstrates Kubernetes monitoring using Prometheus and the Prometheus community Helm chart.

Prometheus runs inside the Kubernetes cluster and collects metrics from Kubernetes components and workloads. Alert rules are configured through Helm values and evaluated by Prometheus.

## Architecture

```text
Kubernetes Cluster
│
├── Prometheus
│   ├── Metrics collection
│   ├── Kubernetes service discovery
│   └── Alert rule evaluation
│
├── Node Exporter
│   └── Node-level metrics
│
├── kube-state-metrics
│   └── Kubernetes object and state metrics
│
├── Alertmanager
│   └── Alert handling
│
└── Pushgateway
    └── Push-based metrics
```

The monitoring stack is deployed in the `monitoring` namespace.

## Deployment

The Prometheus stack is installed using Helm.

The release is named:

```text
prometheus
```

The chart is:

```text
prometheus-community/prometheus
```

The monitoring configuration is stored in:

```text
monitoring/prometheus-values.yaml
```

Install or upgrade the release using:

```bash
helm upgrade --install prometheus prometheus-community/prometheus \
  -n monitoring \
  --create-namespace \
  -f monitoring/prometheus-values.yaml
```

Check the release:

```bash
helm status prometheus -n monitoring
```

Check all monitoring resources:

```bash
kubectl get all -n monitoring
```

## Prometheus Configuration

The values file configures Prometheus alerting rules:

```yaml
serverFiles:
  alerting_rules.yml:
    groups:
      - name: kubernetes-alerts
        rules:
          ...
```

The configuration is passed to the Prometheus Helm chart rather than using Prometheus Operator custom resources.

Therefore, this installation does not use `PrometheusRule` resources.

For example:

```bash
kubectl get prometheusrules -A
```

is expected to fail when the Prometheus Operator CRDs are not installed.

## Alert Rules

### HighCPUUsage

This alert detects sustained high CPU usage.

The expression calculates CPU utilization from the node CPU idle metric:

```promql
100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) by (instance)) > 50
```

The alert fires only when CPU usage remains above 50% for 5 minutes:

```yaml
for: 5m
```

Severity:

```text
warning
```

This demonstrates the difference between a metric crossing a threshold and an alert actually firing after the required duration.

### PodRestarting

This alert detects Kubernetes container restarts:

```promql
increase(kube_pod_container_status_restarts_total[10m]) > 0
```

The expression checks whether a container restart occurred during the previous 10 minutes.

The alert fires after the condition remains active for 2 minutes:

```yaml
for: 2m
```

Severity:

```text
warning
```

## Verify Alert Rules

Check the values used by the Helm release:

```bash
helm get values prometheus -n monitoring
```

Inspect the Prometheus ConfigMap:

```bash
kubectl get configmap prometheus-server -n monitoring
```

Inspect the generated alerting rules:

```bash
kubectl get configmap prometheus-server -n monitoring \
  -o jsonpath='{.data.alerting_rules\.yml}'
```

The output should contain:

```text
HighCPUUsage
PodRestarting
```

## Monitoring Components

### Prometheus

Prometheus collects and stores time-series metrics and evaluates alert rules.

Check the Pod:

```bash
kubectl get pods -n monitoring
```

The Prometheus server is exposed internally through:

```text
prometheus-server.monitoring.svc.cluster.local
```

### Node Exporter

Node Exporter provides node-level metrics such as CPU and system resource usage.

Check it with:

```bash
kubectl get pods -n monitoring -l app.kubernetes.io/name=prometheus-node-exporter
```

### kube-state-metrics

kube-state-metrics exposes metrics about the state of Kubernetes objects.

These metrics are used by rules such as `PodRestarting`.

Check it with:

```bash
kubectl get pods -n monitoring -l app.kubernetes.io/name=kube-state-metrics
```

### Alertmanager

Alertmanager handles alerts generated by Prometheus.

Check it with:

```bash
kubectl get pods -n monitoring -l app.kubernetes.io/name=alertmanager
```

### Pushgateway

Pushgateway provides an endpoint for applications or batch jobs that need to push metrics to Prometheus.

Check it with:

```bash
kubectl get pods -n monitoring -l app.kubernetes.io/name=prometheus-pushgateway
```

## Access Prometheus

Prometheus is exposed internally as a ClusterIP service.

List the services:

```bash
kubectl get svc -n monitoring
```

To access the Prometheus web interface locally, use port forwarding:

```bash
kubectl port-forward -n monitoring \
  svc/prometheus-server 9090:80
```

Then open:

```text
http://localhost:9090
```

The port-forward keeps the service local to the machine running the command.

## Useful Prometheus Queries

Check CPU usage:

```promql
100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) by (instance))
```

Check container restart counters:

```promql
kube_pod_container_status_restarts_total
```

Check container restarts during the last 10 minutes:

```promql
increase(kube_pod_container_status_restarts_total[10m])
```

Check whether the `HighCPUUsage` alert is active:

```promql
ALERTS{alertname="HighCPUUsage"}
```

Check whether the `PodRestarting` alert is active:

```promql
ALERTS{alertname="PodRestarting"}
```

## Alert Testing

### Testing High CPU

The alert condition requires CPU usage to remain above 50% continuously for 5 minutes.

Therefore:

```text
CPU > 50% for less than 5 minutes
    → alert does not fire

CPU > 50% for 5 minutes
    → alert fires

CPU > 50% for 6 minutes
    → alert remains firing
```

This demonstrates how the Prometheus `for` duration prevents short-lived spikes from immediately generating alerts.

### Testing Pod Restarts

A container restart can be simulated in a test environment by restarting or deleting a test Pod.

After the restart, inspect the metric:

```promql
increase(kube_pod_container_status_restarts_total[10m])
```

The `PodRestarting` alert should become active when the expression evaluates to a value greater than zero and remains active for the configured 2-minute duration.

## Verification

A healthy monitoring deployment should show:

* Prometheus server running
* Alertmanager running
* Node Exporter running
* kube-state-metrics running
* Pushgateway running
* Prometheus persistent storage bound
* Alert rules present in the Prometheus configuration

Example:

```bash
kubectl get pods -n monitoring
kubectl get pvc -n monitoring
helm status prometheus -n monitoring
```
